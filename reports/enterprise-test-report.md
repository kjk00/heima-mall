## 万人同时到达购买同一商品

商品为编号1的耳机，每位独立账号购物车预放1件。全部虚拟买家在放行前提交，工作线程统一放行，成功下单后立即演示支付。所有数据写入全新临时SQLite数据库，无自动重试。

这组测量发生于MySQL、Redis改造前，使用真实WSGI请求入口，保留认证、校验与事务。它不包含网络连接、反向代理、FastAPI、Redis或真实支付，也不等于1万条同时执行的HTTP连接。

| 10000 | 10000 | 256 | 9930 | 0 | 70 | 9870 | 60 | 41.29秒 | 36.22秒 |
| 100 | 10000 | 256 | 100 | 9900 | 0 | 100 | 0 | 5.51秒 | 4.17秒 |

库存充足场景有130位买家遇到技术失败，占1.3%；70件库存尚未分配，60笔已创建订单未支付。130条应用错误样本均为 `database is locked`，与10秒SQLite锁等待上限对应。库存始终非负，库存与已预留件数、销量与已支付订单均一致；数据库完整性和外键检查通过。承载能力失败与数据损坏分别判断，此处未发现数据损坏。

另以64工作线程、同样1万虚拟用户和1万库存进行诊断复测：9999次下单成功、1次下单503，9996次支付成功、3次支付503，总耗时37.92秒。降低线程并未完全消除锁超时。报告见 `stress-purchase-10000-workers64.md`。

详细延迟、排队时间、实际处理时间、逐用户响应及13项一致性检查见 `stress-purchase-10000.md` 和同名JSON。响应时间未给定业务SLA，本报告提供实测数据，不将库存守恒视为性能达标。

## 可复现问题

### SEC-001：管理员初始化保留升级前的会话（P1）

位置：`app/admin.py` 的 `admin_setup`。

复现：准备顾客会话A，并复制其Cookie为会话B；A通过本机初始化接口把已有顾客账号升级为终端管理员；A获得新Cookie后，B仍可访问 `/api/admin/auth/me`，返回200。

风险：原有会话持有者随账号升级直接取得全平台权限。建议在同一升级事务中撤销该账号的全部旧会话，再建立新管理员会话。

```bash
.venv/bin/python scripts/enterprise_quality.py --pattern admin_setup
```

### API-001：下单幂等键不验证完整请求一致性（P2）

位置：`app/logic.py` 的 `checkout`。

复现：同一用户使用相同幂等键再次提交完全不同的收货地址，接口返回201及原订单；仅在显式店铺编号不同的情况下检查冲突。

风险：客户端把新请求误认为已执行，得到与输入不一致的订单。建议保存规范化请求摘要，同键不同请求返回409，同键同请求保留重放行为。

```bash
.venv/bin/python scripts/enterprise_quality.py --pattern idempotency
```

### MEDIA-001：不可解码的伪造图片被接受（P2）

位置：`app/admin.py` 的 `admin_upload_image`。

复现：上传只有伪造文件头的33字节PNG、21字节JPEG、30字节WebP，3种情况均返回201。现有校验没有实际解码图片。

风险：损坏素材写入公开素材目录，商品图片不可正常展示。建议执行受尺寸/像素数限制的真实图片解码，必要时重编码后再发布。

```bash
.venv/bin/python scripts/enterprise_quality.py --pattern truncated_images
```

补充验收脚本故意以非零退出码报告这些失败，未用预期失败或跳过掩盖问题。上述3类既有问题本次未修复。

## MySQL与Redis改造说明

默认 `DATABASE_BACKEND=mysql`；连接设置见 `.env.example`。启动入口、管理员工具与迁移工具读取本机 `.env`，外部已导出的变量优先。密码不会写入报告。SQLite可通过显式配置保留，所有自动化业务测试继续使用显式临时SQLite路径。

MySQL使用19张InnoDB表，包括17张业务表、目录缓存状态表及事务守卫表。外键、默认地址唯一约束、退款开放单唯一约束、金额整数分及ISO时间格式保留。应用原来依赖SQLite `BEGIN IMMEDIATE`；当前适配通过共享守卫行锁保留串行写事务语义，尚未改成按商品并行的事务锁定。MySQL连接目前按请求建立，新后端的连接池、容量和故障恢复需要进一步验证。

迁移工具只读源SQLite快照，复制17张业务表，保留账号密码哈希、会话、订单与明细；拒绝含业务数据的目标库，复制和行数校验在一个目标事务中完成。真实数据迁移需明确连接信息和迁移选择后执行；本次未执行。

Redis缓存只覆盖公共目录，key包含数据库命名空间、持久化实例标识、事务内递增的目录版本及查询摘要。商品/店铺变化与版本推进同事务提交，避免Redis不可用时的失效遗漏和旧回填竞争。库存及订单事务不会使用Redis里的库存作为扣减依据。

Redis使用连接池、100毫秒连接/命令超时、禁用自动重试、最多200毫秒回填等待、两秒故障熔断，以及本地互斥锁与Redis持有者校验锁。缓存命中仍读取数据库版本号，因此主要减少公共目录业务查询，不消除数据库读请求或写锁瓶颈。

## 真实接入的阻碍及后续验证

检测到本机MySQL程序与 `/tmp/mysql.sock`；当前执行环境访问该套接字返回权限错误。PyMySQL、Redis和FastAPI依赖未安装；在线下载失败，离线缓存也没有PyMySQL。

尝试在独立临时目录执行不监听网络的MySQL初始化时，mysqld原生进程在执行本项目DDL之前发生SIGSEGV。因此MySQL表结构未完成真实引擎验证，日志见 `mysql-offline-validation.log`；本机已有MySQL数据目录未被修改。

在允许连接服务的环境中，先配置本地MySQL连接并安装依赖，再执行：

```bash
MYSQL_TESTS=1 .venv/bin/python -m unittest tests.test_services.MySQLIntegrationTests -v
REDIS_TEST_URL=redis://127.0.0.1:6379/0 .venv/bin/python -m unittest tests.test_services.RedisIntegrationTests -v
```

MySQL集成测试创建和清理独立 `heima_test_*` 数据库，Redis测试只清理自己的命名空间。之后需要重新开展真实MySQL/Redis万人负载、TCP与反向代理测试，并在修复3类补充验收问题后重新验收。
